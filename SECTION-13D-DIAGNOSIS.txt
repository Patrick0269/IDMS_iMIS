CODE DEFECTS FOUND
1. The shared service-role Supabase client was also used for password sign-in.
   A signed-in user session must not share the privileged database client.
2. The UI offered one ambiguous identifier field for staff and students.
3. login.html redirected to Student Portal when any STUDENT role existed,
   while auth.js redirected only student-only accounts. These rules conflicted.
4. The client did not tell the backend which account type was being used.
5. Backend errors were intentionally generic at the browser boundary; detailed
   causes are available only in backend logs, which is the safer behavior.

SECURITY / DATABASE OBSERVATIONS
1. Identity/RBAC tables have RLS enabled but no browser-facing policies in the
   migration set. Current design intentionally routes privileged data access
   through the backend service key.
2. The secret/service key remains backend-only. The login client uses the
   public publishable key and is isolated per login request.
3. Section 13D removes an owner STUDENT assignment if one appears, removes
   ADMIN/SUPER_ADMIN from the student, and verifies there is no owner-to-student
   row link.
4. Passwords are never written to source, reports, command arguments, or JSON.
   Section 13D collects the new owner password through hidden prompts.

SECTION 13D CORRECTIONS
- Separate Staff/Admin and Student modes in login.html.
- Pass accountType to the backend and enforce it after authentication.
- Use an isolated publishable-key Supabase client for password sign-in.
- Keep the shared secret-key client session-free for database/admin operations.
- Normalize landing-page logic: student-only -> Student Portal; otherwise ->
  administration dashboard.
- Reset and verify the owner password safely.
- Reconcile and verify owner/student role separation.
